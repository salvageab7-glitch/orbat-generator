## 三、出图方案（三选一，请你定夺）

> 这是安卓端最关键的技术决策，直接决定工作量与可用性。Windows 端"只用 spatialillusions 线上站点出图"的约束在安卓同样要满足。

### 方案 A：内置 WebView 渲染（推荐）
- **做法**：App 内嵌 `webview_flutter`，加载 `https://spatialillusions.com/unitgenerator`，通过 `runJavascript` 把 JSON 注入 `#openOrbat` 文件输入或站点 API，等待 `#orbat-svg` 渲染，导出 SVG → 转 PNG。
- **优点**：真正用线上站点渲染（符合"只用线上站点"原则）；无服务器成本；与 Windows 出图完全一致。
- **风险/难点**：① 站点 `#openOrbat` 是 `<input type=file>`，WebView 注入文件需走 Android 的 `WebChromeClient.onShowFileChooser` 桥接（可行但繁琐）；② 移动端 WebView 与桌面 Chromium 渲染行为可能有差异；③ 站点若改版，两端都要跟着改。
- **工作量**：中偏高。

### 方案 B：远程渲染服务
- **做法**：搭一个后端（云函数/轻量服务器）跑 Node+Chrome，安卓上传 JSON → 服务端调 `render_orbat.js` → 回传 PNG/SVG。
- **优点**：安卓端最简单；渲染逻辑与 Windows 共用一套脚本，结果一致。
- **风险/难点**：① 服务器成本与运维；② 用户数据（编制 JSON）上传第三方需隐私考量；③ 离线不可用。
- **工作量**：安卓端低，但多了后端开发运维。

### 方案 C：安卓端不出图（最快）
- **做法**：安卓只做 识图→JSON→校验→审计→导出 JSON；出图必须传回 Windows 端完成。
- **优点**：开发最快、风险最低，完美复用现有 Dart 逻辑（出图那部分直接禁用）。
- **风险/难点**：功能明显缩水，安卓端不能独立出成品图；与"三模式完整能力"的目标有落差。
- **工作量**：低。

**我的建议**：若坚持"安卓也要能独立出图且只用线上站点" → 选 **A**；若接受"安卓侧重转写与校验、出图回 Windows" → 选 **C** 先快速落地。**B 一般不推荐**（成本+隐私）。

## 四、关键技术风险与对策

| 风险 | 对策 |
|---|---|
| DPAPI 是 Windows 专有 | 安卓用 Android Keystore（硬件级）存 AES 密钥，Key 密文格式加 `keystore:` 前缀，与 `dpapi:`/`xor:` 并存兼容 |
| `Process.run` 在安卓不可用 | 出图走第三节选定方案；`renderer.dart` 做 `Platform.isAndroid` 分支 |
| 模式二依赖 `orbat-cli.exe` | 安卓端重新定义（见 P2-3），或明确"模式二在安卓=软件识图+导出" |
| 大图分块与内存 | 复用 `image` 包纯 Dart 切片；安卓注意 Bitmap 内存，限制单块尺寸 |
| 存储权限 | 用 `path_provider` 应用私有目录，避免申请 broad 存储权限；导出走系统分享（file_picker/Share） |
| 站点改版导致两端渲染失效 | 渲染层抽象成接口，Windows/安卓各自实现，共用同一 JSON 契约 |
